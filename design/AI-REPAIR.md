# AI 故障修复

状态：Core、CLI/MCP 与原生 App 已接入同一故障修复会话。HTML仍为交互参照，所有原型实例、模组、日志、回退点与观察均为合成数据，不能作为真实游戏验证通过的证据。

## 从故障现场开始

首页启动失败、游戏异常退出及错误详情使用同一个“AI 分析并修复”入口。进入主 AI 页内的修复会话，固定实例和故障发生时的运行记录；普通聊天与皮肤编辑保持各自用途。重复打开同一故障返回已有修复记录，不能每点一次就创建新任务或重新提交变更。

入口表达一次任务授权：读取本次故障依据，执行当前实例内允许的可回退修复，并自动重启验证。已有模型可直接开始；模型未配置时保留故障上下文，连接后继续。正常退出、独立后台服务的 ERROR 文本与服务器状态查询失败不能一律当作游戏崩溃。

侧栏条目采用12水平/8垂直内距，单行40、带实例副文字56设计单位；标题/状态badge和副文字分别成行。标题省略、badge保留，不能为压缩行高去掉垂直留白。原生使用相同角色与实际字体测量，RTL沿既有流向镜像。

主聊天面板顶部仅保留单行Core状态与撤销，修复会话不重复显示标题、实例名、运行编号、方案原因或范围提示；完整依据继续在原有工具展开详情及结果中查看。输入区域显示固定的关联实例，点击只读查看名称、版本和加载器，不能选择其他实例；模型使用标准下拉框，可以切换下一轮模型。

## 自动推进，按证据结束

一次发起后，自动完成：诊断 → 冻结最小方案 → 保存原状态 → 应用与回读 → 重启 → 读取新运行结果 → 通过或继续修复。方案卡公开列出目标、前后状态、依据和回退方式，但不要求用户逐项点击“应用”“重启”“仍然崩溃”“是否修好”。运行中保留“停止修复”，关闭页面不等同取消后台任务。

- 对明确缺失依赖、Java不匹配等证据，检查实际游戏/加载器/版本范围与本机状态后做最小调整。不能因为搜索结果最新就安装，也不能自动升级整个实例。
- 对疑似模组冲突，将其标为待验证。每次只做有依据的可逆试验；新运行仍出现原异常时，先恢复上一项无效试验，再验证下一个有依据的候选。没有新依据时停止继续修改，不无限枚举或批量停用所有模组。
- 重试关联一个新的、确属当前实例的运行ID；故障运行ID保持不变。原始日志和每次试验的日志、配置、变更与观察分别保留，不能把“最近一次日志”替换成最初故障依据。
- 自动观察进程、窗口、可识别的初始化证据与新错误。异常退出/同一故障签名属于失败；仅有Java进程或窗口不算修复成功，日志中没找到某个字符串也不足以证明成功。
- 启动类问题可得出“本次启动检查通过”。游戏内问题还需复现原场景；缺少复现条件时只询问一次聚焦问题，使用已有特殊`ask_user`问答卡。具备隔离副本及实际游戏自动化后，在副本中复现并保留观察；不能未经能力支持就在原存档中自动操作，或把一次启动通过冒充所有游戏内行为正常。
- 停止请求后先停止继续派发。已提交的效果按现有intent/job记录核对，结果未知时不能重放；恢复操作从核对结果继续。撤销需核对写后状态，避免覆盖玩家之后自行修改的文件。

主结果明确显示验证范围与关联运行：已通过、仍失败、证据不足或尚未覆盖原场景。无需用户反复确认来推动已经可以自动观察的步骤；确实缺失的信息、扩大修改范围或玩家必须亲自完成的操作才打断。

## 现有能力与实际缺口

| 环节 | 已有实现 | 仍需接线或补全 |
| --- | --- | --- |
| 错误与运行依据 | 错误详情“AI分析并修复”调用 Core `StartRepairAsync`；`AiRepairCreate`固定实例及故障运行/准备任务，重复进入复用会话 | 缺少故障记录或仍在运行时，先保留原现场，不把状态查询失败或正常退出作为崩溃 |
| AI读取 | `repair_show`返回原始诊断、当前内容声明/设置及本机Java；自动加载`instance-diagnosis`技能 | 日志及第三方元数据按不可信证据处理；只有缺少工具无法查询的信息才用既有`ask_user` |
| 内容修复 | `repair_plan/apply`复用既有内容启停与Fabric依赖规划/应用；一次只停用一个证据指向的模组，依赖组仅允许新增 | 不自动替换/升级原有模组；不支持的加载器、歧义和无法解析的依赖保留明确原因 |
| 配置与运行时 | 仅选择宿主发现的本机Java及有内存异常依据的小幅堆调整；保存原覆盖值与继承关系，原子前置检查、修改后回读 | 不自动更换整个运行环境；自定义JVM内存参数仍保留其原语义，需要核对最终启动参数 |
| 权限与效果 | 固定实例/故障的持久委托，专用工具目录及`AiToolPolicy`逐次检查；沿用intent和未知效果守卫 | 普通聊天不能借这些工具扩大范围，修复会话也不能调用execute、任意文件或第三方工具 |
| 回退 | `repair_restore`按每次试验的前后收据恢复；错误分类和移除日志头后的异常证据同时匹配时自动回退；保留无关设置与被再次编辑的目标 | 不同异常保留新证据供继续分析，不能仅因同属Mixin/内存错误就断言原故障仍在；回退冲突不强制覆盖，正常关闭请求未完成不强杀 |
| 自动验证 | 每个方案最多一个有持久标签的新Session，进程/窗口、声音及纹理初始化加10秒存活观察；90秒观察预算，原运行证据不变 | `startup_checked`仅表示启动初始化检查，不能证明菜单、世界、服务器或原操作正常；仅窗口或无错误不算通过。游戏内隔离复现/自动化尚未实现 |

一次授权由Core持久化并检查，模型提出的修改仍须经现有typed业务、范围/版本/文件指纹校验与效果守卫。自动执行的依据是Core判定方案符合此次委托，不是让模型伪造人类确认，也不是统一替CLI追加`--confirm`。超出实例、无法回退、未知效果或更大范围的改动沿用具体审核；不能静默升级成全局“允许全部”。

产品仍为CLI/Sprout → Core → 内部Assistant。MEAI继续实际驱动模型/工具回合；修复上下文、有限授权、回退记录、任务和验证事实由Core拥有。App呈现状态与用户选择，不另外实现一个修复Agent循环；CLI/MCP复用功能命令。

实际CLI入口为`ai repair start INSTANCE --session SESSION`（准备失败用`--job JOB`）；`create/show/plan/apply/verify/restore`操作同一Core记录，普通`repair INSTANCE`仍为已有必需游戏文件修复。最多保留六个冻结候选，已尝试的同一候选不重复；证据不足或结果未知时停止盲目修改。模型未配置时先保存故障，选好模型后继续。

## 原型入口与验证范围

大型诊断沿用MCP结果保存与分段读取；修复会话的`result_read`只能读取本次故障工具实际返回并由宿主登记的结果ID，不能猜测读取其它任务。不可因内联输出截断就要求玩家手工摘日志，或把未读到的字段判断为不存在。

启动当前设计静态服务器后，可打开：

- `index.html?page=ai&demo=1&repair=conflict`：第一次试验失败，自动恢复并进行第二次验证，无逐步确认。
- `index.html?page=ai&demo=1&repair=dependency`：明确缺失依赖，一次自动修复/启动检查。
- `index.html?page=ai&demo=1&repair=java`：实例运行时调整。
- `index.html?page=ai&demo=1&repair=runtime`：游戏内错误，启动检查后补充复现条件；后续隔离复现是目标流程示意。
- `index.html?page=ai&demo=1&repair=unknown`：证据不足，保留日志与补充入口，不修改文件。
- 去掉`demo=1`可查看未配置模型时的上下文保留。

首页失败状态和既有错误详情也有实际浏览器内入口。原型仅验证导航、信息层级、状态、自动流程、停止与撤销交互；不调用模型、玩家文件或游戏，不作为Core接线、权限/回退实现或Java/BOT验收。

原生实施时的回归重点是错误归属、有限授权不能扩大、旧方案失效、原状态不被多轮试验覆盖、真实重试失败、未知效果不重放和停止后不继续派发。只有真实进程/日志/持久任务到达对应边界才能声明验证；不为按钮文字和静态样式机械增加测试。
